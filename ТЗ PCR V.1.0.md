>L-CONDS: В рамках MVP v2.0 пользовательский интерфейс — <u>CLI</u>;  
>Интеграции CMDB, Naumen и BotX/CTS временно <u>не используются</u>, но архитектура должна допускать их подключение <u>без переписывания ядра</u>;
>Основным целевым механизмом удалённой перезагрузки для Windows считается <u>WinRM</u>. VMI допускается только как;
>Система должна поддерживать безопасный режим dry-run, при котором команда перезагрузки не отправляется, а <u>только показываются целевые хосты и планируемые действия</u>;
>В MVP v2.0 допускается перезагрузка только хостов из заранее <u>согласованного списка тестовых устройств</u>;
>#MAKEME: Бот ждет 30 секунд и проверяет доступность ПК по ICMP/Ping. Если ICMP заблокирован, допускается дополнительная проверка по состоянию WinRM-порта или другому доступному сетевому признаку;
>#MAKEME: При передаче нескольких хостов обработка должна выполняться параллельно с ограничением числа одновременных задач. Ошибка по одному хосту не должна останавливать обработку остальных;
>

Для MVP лучше основным сделать:
```
--hosts
--file
```

Программе неудобно работать просто со строками.  
Лучше превратить каждый хост в объект задачи.

Концептуально:
```
RebootTask:
  host
  run_id
  dry_run
  timeout_sec
  method
```

После обработки каждого хоста должен быть объект результата.

Концептуально:
```
RebootResult:
  host
  status
  message
  started_at
  finished_at
  duration_ms
  dry_run
  run_id
```
Именно эти результаты потом:

- показываются в консоли;
- пишутся в JSONL;
- позже смогут быть отправлены в Naumen/BotX.

Если сразу думать только “отправить reboot”, то быстро возникнет каша:

- один хост не пингуется;
- второй не прошёл авторизацию;
- третий ушёл в reboot, но мы не поняли;
- четвёртый не разрешён;
- пятый обрабатывался 60 секунд;
- а программа либо упала, либо выдала “всё плохо”, без деталей.

Поэтому правильная модель такая:
```
каждый хост = отдельная задача
каждая задача = свой статус
ошибка одного хоста ≠ падение всей программы
```
