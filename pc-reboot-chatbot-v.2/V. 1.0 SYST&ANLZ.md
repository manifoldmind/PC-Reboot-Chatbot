# 1. Фиксация scope v2.0

## Что делаем сейчас

Упрощённая рабочая версия:

```text
PCReboot CLI
→ пользователь вводит список ПК
→ программа отправляет команду перезагрузки
→ проверяет базовое выполнение
→ выдаёт отбивку по каждому ПК
→ пишет JSONL-лог
```

## Что пока НЕ делаем

Не трогаем:

- `main.py` как будущий бот-оркестратор;
- Naumen;
- CMDB;
- BotX / CTS / мессенджер;
- веб-интерфейс;
- базу данных;
- сложные роли и права;
- мультиязычность;
- полноценный OAuth/SSO.

Это всё потом. Сейчас цель — **безопасный, понятный, тестируемый консольный MVP**.


# 2. Главная мысль версии 2.0

Это уже не “просто скрипт”, а маленькая система. Поэтому сразу разделяем ответственность:

```text
cli.py
  - принимает входные данные
  - валидирует формат
  - вызывает core
  - показывает результат пользователю

core/reboot.py
  - умеет проверить доступность хоста
  - умеет отправить reboot
  - умеет проверить, что хост ушёл в перезагрузку
  - возвращает структурированный статус
  - НЕ печатает пользователю
  - НЕ знает про CLI-аргументы

logs/
  - хранит JSONL-отбивки
  - каждая строка — отдельное событие
```

Это важно для будущего бота:  
`core/reboot.py` потом сможет вызывать и CLI, и бот, и тесты.


# 3. Обязательные условия безопасности

До любой реализации нужно зафиксировать правила.

## 3.1. Только тестовые машины

Нельзя начинать с рабочих пользовательских ПК.

Минимально нужен хотя бы один безопасный тестовый объект:

- тестовая VM;
- или старый лабораторный ПК;
- или стенд, где перезагрузка допустима;
- желательно со снапшотом или возможностью быстро восстановить.

Если такого нет — сначала делаем только **dry-run**, без реальной отправки reboot.

>[!NOTE] [x] ПК будут выделены
## 3.2. Явное подтверждение

Для реального reboot должен быть отдельный режим.

Например, логика такая:

```text
По умолчанию: dry-run
Явно включить реальный режим: --apply
```

Это защитит от случайного перезапуска.

## 3.3. Белый список хостов

Очень желательно завести файл разрешённых тестовых хостов.

Например:

```text
allowed_hosts.txt
```

Идея:

- если хост не в белом списке — не перезагружаем;
- для MVP это не полноценная безопасность, но защита от ошибки ввода.

## 3.4. Никаких паролей в коде

Если нужны учётные данные:

- переменные окружения;
- `.env` локально, но не в git;
- или запрос пароля в runtime;
- или использование текущей доменной сессии, если это допустимо.

В логах пароли быть не должно.

# 5. Ключевой архитектурный вопрос: чем именно делаем reboot?

Это самый важный вопрос сейчас.

В ТЗ указан WinRM/SSH. Но на практике есть несколько возможных механизмов.


## Вариант A. Честный WinRM

Например, через Python-библиотеку `pywinrm`.

Плюсы:

- ближе к ТЗ;
- хорошо ложится в будущую архитектуру;
- можно выполнять команды удалённо через WinRM.

Минусы:

- нужно, чтобы WinRM был реально настроен;
- нужны правильные права;
- нужно понимать аутентификацию: NTLM / Kerberos / CredSSP;
- могут быть проблемы с HTTP/HTTPS, TrustedHosts, firewall.


## Вариант B. PowerShell Remoting через внешний вызов

Например, из Python дёргать `Invoke-Command`.

Плюсы:

- часто проще в доменной среде;
- использует готовые механизмы Windows.

Минусы:

- зависимость от PowerShell;
- нужно аккуратно обрабатывать ошибки;
- всё равно нужно понимать WinRM.


## Вариант C. Встроенный `shutdown /r /m \\HOST`

Это не WinRM. Это remote shutdown через RPC/SMB-механику Windows.

Плюсы:

- очень просто в домене;
- часто работает, если есть права администратора;
- не требует явной настройки WinRM.

Минусы:

- это не WinRM;
- может быть запрещено ИБ;
- нужны открытые соответствующие RPC-доступы;
- менее универсально для Linux.


## Мой наставнический вопрос к тебе

Какой механизм мы считаем целевым для v2.0?

Выбери один:

1. **WinRM через Python**
2. **PowerShell Remoting**
3. **Remote shutdown command**
4. **Смешанный режим**: сначала MVP на shutdown, потом переход на WinRM
5. **Пока не знаю, нужно выбрать вместе**

От этого зависит весь следующий шаг.


# 6. Важное разделение: reboot и проверка reboot

Это разные вещи.

## 6.1. Отправка команды

Это действие:

```text
“перезагрузись”
```

Оно может завершиться успешно, даже если ПК потом не перезагрузился.

## 6.2. Проверка ухода в reboot

Это уже наблюдение:

```text
хост перестал отвечать?
появился/пропал ping?
порт WinRM пропал?
```

В ТЗ указано:

- таймаут операции: 60 секунд;
- после отправки команды ждём 30 секунд;
- проверяем доступность по ICMP/Ping, чтобы убедиться, что ПК ушёл в перезагрузку;
- полная проверка после ребута пока не требуется.

Это разумно оставить и в v2.0.


# 7. Как обрабатываем несколько ПК одновременно

Ты правильно отметила: если одновременно несколько ПК — это отдельная особенность.

## Правильная идея

Не делать строго последовательно, если хостов много.  
Но и не запускать “всё сразу без ограничений”.

Нужен **ограниченный пул задач**.

Например:

```text
max_workers = 5
```

или

```text
max_workers = min(8, количество хостов)
```

## Почему не “всё сразу”

Потому что:

- можно перегрузить сеть;
- можно упереться в лимиты домена;
- сложнее отлаживать;
- может быть много одновременных таймаутов.

## Правило

Один хост упал — другие продолжаем обрабатывать.


# 8. Статусы, которые нужно спроектировать заранее

Перед кодом очень полезно продумать статусы. Это не код, а модель.

Предлагаю минимум такие:

```text
PENDING
VALIDATION_FAILED
NOT_ALLOWED
PRECHECK_FAILED
AUTH_ERROR
COMMAND_SENT
REBOOT_CONFIRMED
TIMEOUT
COMMAND_ERROR
SKIPPED
UNKNOWN_ERROR
```

Почему это важно:

- потом легко писать отчёт;
- потом легко маппить на Naumen;
- тесты становятся понятнее;
- не будет кашы из “вроде success / вроде fail”.


# 9. Минимальная модель результата на один хост

Для каждого хоста хорошо бы хранить не просто “ок / не ок”, а структуру.

Например, поля:

```text
host
status
message
started_at
finished_at
duration_ms
method
dry_run
run_id
```

Это уже почти будущая интеграция с логированием и Naumen.


# 10. Что должно быть в логах

## Формат

Для MVP отлично подходит **JSONL**:

- одна строка = один JSON-объект;
- легко читать;
- легко парсить;
- соответствует духу ТЗ.

## Что писать

Минимум:

```text
timestamp
run_id
host
stage
status
method
duration_ms
error_type

```

## Чего НЕ писать

- пароли;
- токены;
- секреты;
- лишние персональные данные;
- полные дампы конфигов.


# 11. Как проектировать CLI

Ты написала:

> введите в консоль список пк для ребута

Тут есть важный выбор.

## Возможные варианты ввода

### Вариант 1. Через аргумент командной строки

Например:

```text
python cli.py --hosts PC-01,PC-02
```

Плюсы:

- легко тестировать;
- легко автоматизировать;
- удобно для CI.

### Вариант 2. Через файл

Например:

```text
python cli.py --file hosts.txt
```

Плюсы:

- удобно для списка машин;
- меньше ошибок ручного ввода.

### Вариант 3. Интерактивный ввод

Например:

```text
Введите список ПК через запятую:
```

Плюсы:

- ближе к формулировке “введите в консоль”.

Минусы:

- сложнее тестировать;
- хуже воспроизводимость.

## Моя рекомендация

Для MVP лучше поддержать сначала:

```text
--hosts
--file
--dry-run
--apply
```

А интерактивный ввод добавить потом, если захочется.


# 12. Что должен делать `cli.py`

Он должен быть тонким.

## Его задачи

1. Разобрать аргументы.
2. Загрузить список хостов.
3. Проверить, что список не пуст.
4. Применить белый список, если есть.
5. Вызвать core для каждого хоста.
6. Собрать результаты.
7. Показать сводку.
8. Записать итоговый лог.
9. Вернуть правильный exit code.

## Чего ему лучше не делать

- не ходить напрямую в WinRM;
- не делать ping-логику вручную внутри CLI;
- не содержать бизнес-правила перезагрузки.


# 13. Что должен делать `core/reboot.py`

## Его задачи

1. Принять host и параметры выполнения.
2. Выполнить pre-check.
3. Отправить reboot.
4. Дождаться подтверждения ухода в reboot.
5. Вернуть статус.

## Очень важно

`core/reboot.py` **не должен печатать в консоль**.

Он возвращает данные. Печатает CLI.

Это сделает код тестируемым.


# 14. Как строить цикл WORKING ↔ TESTING

Не надо писать всё сразу.

Идём так:

## Шаг 0. Подготовка стенда
Проверить:

- есть ли тестовый ПК/VM;
- есть ли права;
- какой транспорт выбран;
- есть ли сетевой доступ;
- можно ли выполнять reboot.

## Шаг 1. Dry-run CLI
Сделать так, чтобы:

- принимался список хостов;
- ничего не отправлялось;
- выводился планируемый список действий.

## Шаг 2. Pre-check одного хоста
Проверить:

- имя резолвится;
- ping проходит или не проходит;
- WinRM порт доступен, если выбрали WinRM.

## Шаг 3. Одиночный reboot
Отправить reboot только на одну тестовую машину.

## Шаг 4. Подтверждение reboot
Научиться понимать:

- хост пропал;
- хост не пропал;
- таймаут;
- неопределённый статус.

## Шаг 5. Логирование
Добавить JSONL-строки.

## Шаг 6. Несколько хостов
Добавить параллельную обработку.

## Шаг 7. Отчёт и exit codes
Сделать понятную сводку.

## Шаг 8. Ручные тест-кейсы
Прогнать список сценариев.


# 15. Тест-кейсы, которые нужно продумать заранее

Это очень важно, потому что ты хочешь не “чтобы просто работало”, а чтобы система была проверяемой.

## TC-1. Пустой список хостов
Ожидаем:

- ошибка ввода;
- reboot не отправляется.

## TC-2. Невалидный формат списка
Например, пустые строки, лишние запятые.

Ожидаем:

- нормальная обработка;
- понятное сообщение.

## TC-3. Dry-run
Ожидаем:

- ничего не перезагружается;
- виден список целей;
- виден режим dry-run.

## TC-4. Хост не разрешён в white list
Ожидаем:

- статус `NOT_ALLOWED`;
- reboot не отправляется.

## TC-5. Хост недоступен
Ожидаем:

- статус `PRECHECK_FAILED`;
- reboot не отправляется.

## TC-6. Ошибка доступа
Ожидаем:

- статус `AUTH_ERROR` или `COMMAND_ERROR`;
- понятная причина.

## TC-7. Один тестовый ПК успешно перезагружен
Ожидаем:

- статус `REBOOT_CONFIRMED`;
- есть запись в логе.

## TC-8. Несколько хостов, один падает
Ожидаем:

- обработка остальных продолжается;
- сводка корректная.

## TC-9. В логах нет секретов
Проверить глазами и, позже, автотестом.


# 16. Какие пробелы нужно быстро проверить у себя

Чтобы реализовать v2.0 осознанно, нужно убедиться, что ты понимаешь следующие темы.

## Сеть
- что такое hostname / IP / DNS;
- что такое ICMP ping;
- что такое TCP port;
- почему ping может не проходить даже при живом хосте.

## Windows / домен
- что такое доменная учётка;
- что такое права администратора;
- чем отличаются локальный админ и доменный админ;
- что такое remote shutdown / WinRM / PowerShell Remoting.

## WinRM
- что это за служба;
- какие порты использует: 5985 HTTP, 5986 HTTPS;
- что нужно, чтобы клиент мог подключиться;
- что такое TrustedHosts;
- какие бывают аутентификации.

## Python
- как передавать аргументы в скрипт;
- как читать файл;
- как писать JSONL;
- как обрабатывать исключения;
- как запускать задачи параллельно;
- как не смешивать бизнес-логику и вывод.

## Тестирование
- что такое тест-кейс;
- чем dry-run отличается от реального запуска;
- как проверять ошибки, не ломая систему.

Если по какому-то пункту сейчас “не уверена” — это нормально. Это и есть те самые пробелы, которые будем закрывать по ходу.
