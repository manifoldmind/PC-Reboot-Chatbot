Запомни один главный принцип: **код течёт только в одну сторону — слева направо**, как вода по трубам:

```
 💡 сырой код / эксперименты      ✅ сборка и тесты           🚀 релиз
        │                              │                       │
  [ mindground ]  ── merge ──▶  [ made ]  ── только PR ──▶  [ main ]
     «мастерская»               «сборочный цех»            «склад готового продукта»
```

### Роли веток (резюме)
- 🌱 **`mindground`** — сюда ты коммитишь каждый день. Прототипы, сырой код, эксперименты с API Naumen/CMDB, черновики FSM. Здесь можно ошибаться и переписывать.
- 🛠️ **`made`** — сюда попадает только то, что **уже работает и покрыто минимальными тестами** (S.T.E.P. → *Test minimally*). Здесь модули собираются вместе и проходят интеграционную проверку.
- 🚀 **`main`** — эталон для деплоя. Прямой пуш физически закрыт ruleset'ом; вход только через Pull Request из `made`.

### Типовой цикл для этапа ТЗ (например, Этап 1: FSM-ядро)
```bash
# 1) Работаем в мастерской
git checkout mindground
# ...пишем код...
git add .
git commit -m "FEAT: ядро FSM и сценарий диалога"
git push origin mindground

# 2) Модуль готов и проверен → собираем в made
git checkout made
git pull origin made
git merge mindground
git push origin made
# ...прогоняем тесты, проверяем интеграцию...

# 3) Сборка стабильна (конец этапа / перед релизом) → PR на GitHub:
#    Pull requests → New pull request → base: main ← compare: made → Merge
```

### Четыре правила дисциплины
1. **В `main` — никогда напрямую.** Даже одной строкой. Только PR из `made`.
2. **В `made` — без «сырца».** Не работает у тебя локально — не покидает `mindground`.
3. **Коммиты с маркерами**, как уже повелось в проекте: `INIT:`, `ADD:`, `UPD:`, `FEAT:`, `FIX:`, `TEST:`, `DOCS:` — по истории сразу видно, что происходило.
4. **Раз в несколько дней — синхронизация «вниз»**, чтобы ветки не расходились: смержила PR в `main` → `git checkout made && git merge main` → `git checkout mindground && git merge made`.

Всё, фундамент Git-процесса готов и защищён. 🎉

## Шаг 4. Когда v2 (следующая версия разработки) будет готова к релизу

**А) Создать тег** (для маркировки релиза в `mindground`):

powershell

git tag v2.0
git push origin v2.0

**Б) Создать отдельную ветку с историей только для папки `src`** (аналогично тому, как мы сделали для v1.2):

powershell

git subtree split --prefix=src -b feature/v2.0-mvp
git push origin feature/v2.0-mvp --force

Теперь в ветке `feature/v2.0-mvp` будет только код из `src`, со всей историей изменений этой папки.
