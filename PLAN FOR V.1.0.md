Принято. **PLAN v2.0 — умный ход.** Мы выносим самую рискованную интеграцию (реальный WinRM-ребут) в отдельную консольную версию и тестируем её **до** того, как обернём в бота. По S.T.E.P. это «test the risky thing first». Бонус: консольный харнес станет **диагностическим прибором** — он сразу покажет, на каких ПК реально включён WinRM и где открыт файрвол (наши открытые вопросы к админам получат ответы в виде данных).

Ключевое архитектурное решение: **консоль — это ещё один «пульт» поверх того же `core/reboot.py`**. Бот (`main.py`) и консоль (`cli.py`) — два оркестратора над одним ядром. Ничего не переписываем.
```
CLI-слой
  ↓
Ядро управления перезагрузкой
  ↓
Бэкенд Windows WinRM
  ↓
Целевой ПК
```
>[!NOTE] **v2.0 — это CLI-обёртка над будущим ядром PCReboot, где Windows-бэкенд работает через WinRM.**

```
pc_reboot_chatbot/
├── cli.py              # 🆕 консольный пульт (WORKING<->TESTING)
├── main.py             # будущий бот-оркестратор (пока не трогаем)
├── core/
│   └── reboot.py       # 🆕 РЕАЛЬНЫЙ WinRM-бэкенд + ping-проверка
└── logs/               # отбивки JSONL
```

### 🎛 Решения под новые условия (LIST CONDS)

| Условие | Решение |
|---|---|
| Обычный физический ПК в домене + админская УЗ | Используем **нативный Windows Remoting (PowerShell `Invoke-Command`)** — он идёт по WinRM и сам берёт **Kerberos-билет текущей УЗ**. Секреты в `.env` для этой версии **не нужны** (ИБ это понравится). `pywinrm` с кредами из `.env` оставим на версию бота |
| Запуск по согласованию с ИБ | `--dry-run` (показать план без отправки) + интерактивное подтверждение перед боевым запуском |
| Одновременный ребут нескольких ПК | `ThreadPoolExecutor`: каждый ПК — независимый поток; падение одного не убивает остальных; лимит воркеров; агрегированный отчёт |
| Отбивка о работе | Живой вывод по мере готовности + итоговая таблица + JSONL-лог (ТЗ «Логирование») |

### 🧪 Порядок испытаний (сначала безопасно, по согласованию с ИБ)

```powershell
# консоль запущена ПОД админской доменной УЗ (Kerberos работает из коробки)
python cli.py --dry-run WS-K534D WS-K534F        # 1) план без отправки
python cli.py WS-K534D                            # 2) ОДИН тестовый ПК, руками подтвердить
python cli.py --file pcs.txt --check              # 3) несколько одновременно + ping-отбивка
```

Ожидаемые «диагнозы» в отбивке — это и есть ответы на открытые вопросы: `unreachable` = WinRM выключен/файрвол закрыт; `access_denied` = УЗ не локальный админ на целевом ПК (GPO); `command_accepted` + `went_down=true` = **цепочка работает end-to-end**. ✅
